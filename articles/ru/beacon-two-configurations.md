# Две конфигурации Beacon в одном файле: почему первое совпадение недостаточно

Автор: Дмитрий Кудрявцев · 24 октября 2026 года · C2 Client Analyzer 0.1.0

[English](../en/beacon-two-configurations.md) · [Главная](../../README.ru.md)

При разборе одного исследовательского образца C2 Client Analyzer нашёл два структурно подходящих блока конфигурации Beacon. Адрес, порт и несколько числовых параметров у них совпали. Однако блоки различаются по другим данным. Выбрать первый и назвать его рабочей конфигурацией означало бы сделать вывод, которого статический разбор не подтверждает.

В этой статье рассматривается извлечение конфигурации из байтов файла. Образец не запускался; соединений с извлечённым адресом не выполнялось. Дизассемблирование, анализ потока управления и определение активного блока в этот разбор не входят.

## Исходные данные и проверяемый вопрос

Образец взят из публичного исследовательского набора Sentinel-One/CobaltStrikeParser, зафиксированного на commit `2703878a74811d047efde815429b78719afed357`. Название кейса в проекте — `beacon-xor69-multiple`.

- Размер файла: **408 716 байт**.
- SHA-256 файла: `4d1d732125e4d1a3ba0571e0cd892cf8e0dce854387ee405f75df4dcfb0f616b`.
- SHA-256 исходного ZIP: `2ce0a1fd96fe5073a6ba12bd69e7ccdb36ab97a607fbe17085ae2069d08313eb`.

Вопрос узкий: сколько блоков в этом файле проходят поддерживаемые структурные проверки парсера и чем различаются извлечённые данные? Эти проверки не устанавливают подлинность конфигурации, версию продукта или принадлежность к кампании.

[Источник, хеши и ожидаемый отчёт](https://github.com/mejustbox-byte/c2-client-analyzer/blob/v0.1.0/cases/manifest.json).

## Как ищется и проверяется блок

Парсер ищет шестибайтовый заголовок первого поддерживаемого TLV-поля в открытом виде и с фиксированным XOR `0x69` или `0x2e`. Для данного образца оба принятых блока используют `0x69`. Такой ключ описывает кодирование; сам по себе он не доказывает версию Beacon.

После декодирования ограниченного участка читаются три big-endian значения: ID поля, тип и длина. Проверяются допустимые типы, границы, отсутствие повторных ID и наличие обязательных полей `1`, `2`, `3`, `8`. Для числовых полей проверяется соответствующая длина; для поддерживаемых текстовых полей — допустимое представление.

В версии 0.1.0 действуют лимиты: до 32 кандидатов на файл, до 4096 декодируемых байт на кандидат, до 128 полей в блоке и до 2048 байт в поле. Это ограничивает объём обработки недоверенных данных, но не обеспечивает поддержку всех вариантов конфигурации.

## Что получилось

Все смещения ниже — **десятичные файловые смещения**, а не виртуальные адреса.

| Параметр | Блок A | Блок B |
| --- | --- | --- |
| Начало блока | `191016` | `395452` |
| Кодирование | XOR `0x69` | XOR `0x69` |
| Потреблено байт при разборе, включая терминатор | `655` | `655` |
| Поле 2: порт | `327` | `327` |
| Поле 3: `sleep_ms` | `18272` | `18272` |
| Поле 4: `max_get_bytes` | `1048576` | `1048576` |
| Поле 5: `jitter_percent` | `0` | `0` |
| Адрес из поля 8, в обезвреженном виде | `185[.]154[.]52[.]207` | `185[.]154[.]52[.]207` |
| URI из поля 8, в обезвреженном виде | `/GG[.]GG` | `/GG[.]GG` |

Совпадение этих параметров не делает блоки идентичными. **Поле 7 размером 256 байт имеет разные SHA-256:**

- Блок A: `c3edf49d83e1ea668000f6d9e90490316db58894176c2c332f7eaf397aceaed0`.
- Блок B: `2c2c7de1a12e59da75232ddd2cc3edde1142f86c8c42d260f284767bded3646f`.

В этой версии поле 7 не интерпретируется: отчёт сохраняет хеш его значения. Различие хешей показывает различие байтов, но не объясняет их назначение.

Различается и поле 9, интерпретируемое как User-Agent: в одном блоке есть фрагмент `WGGdGGG`, в другом — `WGGcGGG`. Необычное содержимое сохраняется в отчёте, без попытки восстановить «правильную» строку по догадке.

Для проверки отдельного значения можно взять поле 2 блока A: его заголовок начинается на `191024`, значение — на `191030`. После XOR-декодирования двух байт значение читается как big-endian число `327`. Так результат связывается с конкретным участком файла.

[Полный ожидаемый отчёт](https://github.com/mejustbox-byte/c2-client-analyzer/blob/v0.1.0/cases/beacon-xor69-multiple.expected.json).

## Почему результат — `ambiguous`

Парсер подтвердил два структурных совпадения. Он не установил, какой блок читается при исполнении и читается ли какой-либо из них вообще. Несколько блоков могут иметь разные объяснения, но выбор объяснения потребует дополнительных данных.

Поэтому сохраняются оба блока, их смещения и различия. Статус `ambiguous` обозначает неоднозначность выбора конфигурации в рамках этой процедуры, а не доказательство двух активных сетевых каналов.

В работе SOC извлечённый адрес может стать основанием для поиска по разрешённым журналам. Даже точное совпадение адреса и порта в предоставленной записи не докажет, что соединение создал именно этот файл: нужны данные об источнике события, процессе и времени. Следующим исследовательским шагом может быть проверка ссылок на блоки в коде или наблюдение их чтения в отдельно подготовленной лаборатории. В этом кейсе такие шаги не выполнялись.

## Как повторить результат

Используйте checkout тега `v0.1.0` и установку по [инструкции проекта](https://github.com/mejustbox-byte/c2-client-analyzer/blob/v0.1.0/docs/ru/user-guide.md). Порядок получения исходного исследовательского ZIP с закреплённого commit приведён в [разборе релиза](https://github.com/mejustbox-byte/c2-client-analyzer/blob/v0.1.0/docs/ru/cases.md). Для работы с враждебными файлами нужна отдельная среда анализа.

Для уже полученного архива выполните из корня checkout, указав новый выходной файл:

```sh
python scripts/reproduce_case.py --case beacon-xor69-multiple --archive work/beacon-xor69-multiple.zip --verify --output work/beacon-xor69-multiple.json
```

Скрипт сверяет хеш ZIP, выбирает конкретный файл, проверяет его хеш и анализирует байты в памяти без извлечения на диск. `--verify` требует побайтового совпадения с сохранённым отчётом. Код `0` этой команды означает успешное повторение; сам отчёт сохраняет `status: ambiguous`. При обычном CLI-извлечении неоднозначный результат возвращает код `2`.

Практическое правило этого кейса: при нескольких подходящих конфигурациях сохранять происхождение каждого поля и неопределённость выбора. Первое найденное смещение — свойство поиска, а не доказательство активности блока.
